# Development workflow

## Artifacts

| Artifact | Owner | Definition | Goal | Scope | Out of scope |
|---|---|---|---|---|---|
| Requests | `key-account-manager` | A request for the software to do something new or differently. | Record what is expected from the software by stakeholders, so that requirements are grounded in real needs and nothing is lost, softened, or invented. | Verbatim statements with requester and context; triage status; theme and affected area; severity with its basis; evidence; open questions. In-session only: no files, no registry, no memory across sessions. Handed-over items are forgotten. | Requirements, rules, tasks, plans, designs, and code. |
| Requirements | `requirements-engineer` | A documented representation of a need, capability, or property the software shall have. Business requirements focus on function — what the software shall do. Non-functional requirements (quality requirements) state how well the software must perform the function and are usually described by their importance and quality attributes. | State what the system shall do and how well, in a validated, traceable, consistent form that planning can rely on and verification can test against. | Business requirements (REQ) and non-functional requirements (NFR: quality requirements and constraints), with user story, description, criticality, acceptance criteria, rationale, verification method, references, and labels; includes elicitation, documentation, validation, and traceability. | Solution design, architecture decisions, tasks, and code. |
| Business Rules | `business-analyst` | A rule, formula, or way of deciding an outcome required for the fulfilment of a requirement. | State the decision logic and constraints of the business domain that implementation must obey. Every rule must help fulfil a requirement. | Rule statement, rationale, applicability, exceptions, source requirement traceability, and validation status. | Requirements themselves, technical validation logic, and UI behavior. |
| Business Glossary | `terminologist` | A list of terms and their meanings. | Maintain one canonical meaning per business term, so requirements, rules, domain model, specifications, UI text, tickets, and code use the same language. | Canonical term, definition, synonyms, homonyms, acronyms and abbreviations, cross-references, and deprecated variants. | Entity and attribute design (domain model) and code identifiers. |
| Domain Model | `domain-modeler` | An abstract model of a domain with its contexts, objects, and processes, describing phenomena in an application domain. | Describe the business domain independently of implementation, so requirements are understood in their real context and solutions use consistent concepts. | Context map, business object model, state diagrams, attribute lists, and business process diagrams. | Technical architecture, code structure, and UI design. |
| Architecture | `architect` | The design principles, properties, and evolution strategy of a system. | Fix the fundamental structure, global solution design, and technology stack so that quality requirements are met and the system can evolve coherently. | Architecture description with context, building-block, runtime, and deployment views; global solution design; technology stack selection (languages, frameworks, platforms, infrastructure); external interfaces and contracts; cross-cutting concepts; NFR coverage; architecture decisions, alternatives, and rationale. | Requirement content, detailed design, and source code. |
| Technical specification | `architect`, `tech-writer` | A systematically represented description of the properties of the feature to be implemented, covering behavior, flows, states, data, interfaces, and constraints. | Turn validated requirements and architecture decisions into an implementation-consumable specification that implementation and verification can rely on. | Feature behavior, flows and states, data and API-facing attributes, validation and error behavior, interface contracts, and traceability to REQ/NFR and decisions. | Business requirements, roadmap order, and source code. |
| Backlog | `planner` | An ordered list of tasks, milestones, and releases planned to reach the expected state of the developed software. | Turn validated requirements into an ordered, dependency-safe delivery plan that the orchestrator can execute without re-planning. | Feature roadmap, feature priority encoded, milestones, releases, high-level feature tickets, dependencies, release assignment, and dependency-graph validation. | Ticket-level scope and acceptance criteria (task-refiner), execution status and approvals (orchestrator). |
| Implementation plan | `task-refiner` | A description of the implementation details of a task. | Make a single ticket self-contained and implementation-ready, so implementation and review need no further clarification. Follow the technical specification and architecture defined. | Ticket scope, user story, behavior, acceptance criteria, affected REQ/NFR IDs, UI and specification references, technical notes, and test expectations. | Architecture decisions, implementation code, and roadmap order. |
| UI Specification | `ui-designer` | A systematic description of the expected user interface. | Describe the user interface in words precisely enough that design, implementation, and review work from one shared understanding of screens, layout, navigation, and states. | UI description documents: screen inventory, layout regions, navigation, UI states, interaction behavior, validation and message expectations, and platform differences. Layout only. | Technology and library choices, production styling assets, backend behavior, and clickable prototypes. |
| UI Mockups | `ui-designer` | A graphical description of the expected user interface. | Provide layout, navigation, and design for the happy-path flow, so they can be agreed and approved before code is written. | One self-contained clickable HTML mockup per affected ticket, covering the current feature's happy path per platform, with a review landing and navigation between screens; approval state. | Production styling assets, technology choices, backend behavior, and the UI specification itself. |
| Source Code and Tests | `android-dev`, `backend-dev`, `frontend-dev`, `rust-dev` | An artifact that can be compiled or interpreted to provide functionality to the user. | Implement the specified behavior and verify it, so acceptance criteria and quality requirements are demonstrably met. | Production code, unit and integration tests, and build and dependency configuration. | Requirements, plans, design approval, and review verdicts. |
| Quality Review Report | `quality-gatekeeper` | An assessment of an implementation and an evaluation of its fulfilment of acceptance criteria and definition of done. | Independently establish whether a completed ticket satisfies its acceptance criteria and definition of done before the user is asked to approve it. | Per-criterion evidence, test and build results, verification of scope, detected gaps or scope creep, and a pass/fail verdict with findings. | Fixes, requirement changes, and the approval decision itself. |
| Security Audit | `security-officer` | An assessment of an implementation and an evaluation of its vulnerability to malicious use and abuse. | Independently assess security risk for a release and give a release recommendation based on evidence rather than assumption. | Secrets, dependency supply chain, authentication and authorization, input handling, data protection, platform-specific risks, and security NFR coverage; severity-ranked findings with owners and a Pass / Pass with findings / Block decision. | Remediation implementation and functional testing. |
| Code Audit | TBD | An evaluation of code and test quality. | Verify that the code and tests are maintainable and clean. | Complexity, duplication, naming, structure, test coverage and quality, style-guide compliance, and maintainability findings with severity. | Functional verification, security assessment, and fixes. |

*Acceptance criteria*: "The criteria that a work product must satisfy to be accepted by the stakeholders"; in agile development, the criteria that the implementation of a backlog item must satisfy.
