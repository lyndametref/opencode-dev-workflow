# Development workflow

## Artifacts

Every artifact is defined with the same fields, in the same order, so definitions can be compared and reviewed one artifact at a time.

| Field            | Meaning                                                                                             |
| ---------------- | --------------------------------------------------------------------------------------------------- |
| Definition       | What the artifact is, without policy or process                                                     |
| Goal             | Why the artifact exists and what it is for                                                          |
| Granularity      | The unit an instance is created for (request, feature, milestone, task, release, change)            |
| Owner / approver | Who owns the content and who approves it                                                            |
| Produced by      | The phase and task kind that creates or updates it                                                  |
| Lifecycle        | The states an instance moves through                                                                |
| Required fields  | The content every instance must carry; an artifact is complete when every required field is present |
| Dependencies     | What this artifact depends on: inputs it must stay consistent with                                  |
| Dependents       | What depends on this artifact: consumers that must follow it; derived from their `Dependencies`     |
| Related          | Peer artifacts or records, with neither derivation nor ordering                                     |
| Never contains   | The content that belongs to another artifact                                                        |
| Verified by      | The check and phase that prove it is met                                                            |

Ownership is not absolute: an artifact's `status` and `references` may be updated by the actor that records them, and an owner may verify its own artifact when it has the best understanding of it. Coordination artifacts (Backlog, Task) are owned but not single-editor: the owner is accountable for the result, and the actors of each phase edit their own fields.

Tasks use the same three fields: for them, `Dependencies` is an ordering constraint, and the target must be `Done` before the dependent starts.

`*not defined*` marks a field the workflow does not yet specify. A `Notes` row appears only where existing text is not yet classified as one of the fields above. Both are review targets, not omissions by accident.

**Verification and approval.** Verification is the act of checking a work product; approval is the recorded result of a verification completed positively. Where an artifact requires user verification, the user verifies it, and a positive verification approves the artifact — the artifact's `approved` state records that result.

### Requests

| Field            | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | A stakeholder's need for the software to do something new or differently, summarized in canonical business terminology before analysis and kept as a persistent record.                                                                                                                                                                                                                                                                                                                                                             |
| Goal             | Record what is expected from the software by stakeholders, so that requirements are grounded in real needs and nothing is lost, softened, or invented.                                                                                                                                                                                                                                                                                                                                                                              |
| Granularity      | One per request. A request is described by one or more items; an item is an aspect of the request, and the items of one request are handled only together, never split into separate requests.                                                                                                                                                                                                                                                                                                                                      |
| Owner / approver | `key-account-manager` (all content) / requester (confirms the content is faithful at creation). `status` and `references` are the only fields another actor may update, each from the step that records it.                                                                                                                                                                                                                                                                                                                         |
| Produced by      | Phase 1 Request intake, `key-account-manager`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| Lifecycle        | `open` → `in-progress` (requirements work, or planning for a `bug`, has started)<br/>`open` → `parked` (the requester agrees to hold the need for later)<br/>`parked` → `in-progress` (intake reactivates it when its time has come)<br/>`open`, `parked`, `in-progress` → `closed` (the work is planned)<br/>`open`, `parked`, `in-progress` → `rejected` (the need will not be fulfilled, with a reason)<br/>`closed` and `rejected` are terminal. Before creation the request exists only in the session and is not an artifact. |
| Required fields  | Artifact: identifier, title, category (`bug`, `enhancement`, `technical-improvement`), requested outcome, status (`open`, `parked`, `in-progress`, `closed`, `rejected`), references, requester confirmation.<br/>Item: item number, statement with requester and context, theme and affected area, open questions, references.<br/>Grouping: theme group, with cross-cutting quality concerns in a separate group.                                                                                                                 |
| Dependencies     | none                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Dependents       | requirements created or modified, recorded on the affected item; tasks, once a `bug` or `technical-improvement` request is planned                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Related          | overlapping requests considered for merging                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| Never contains   | Requirements, acceptance criteria, user stories, business rules, priority, scope, solution, architecture, design, estimates, tasks, milestones, and releases.                                                                                                                                                                                                                                                                                                                                                                       |
| Verified by      | Phase 1 creation criteria, before creation; Phase 2 input check, which returns an incomplete or missing artifact to Phase 1; Phase 3 closure check, which confirms the status and the references.                                                                                                                                                                                                                                                                                                                                   |
| Notes            | `bug` requests go directly to planning.<br/>Open requests are listable on demand; parked requests are listed separately and reactivated by intake when their time has come.<br/>Items are aspects of one need and are handled together; a request is never partially closed.                                                                                                                                                                                                                                                        |

### Requirements

| Field            | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | A documented representation of a need, capability, or property the software shall have. A business requirement states what the software shall do; a non-functional requirement states how well it must do it, as an observable and achievable quality attribute or constraint.                                                                                                                                                                                                                                                                                                                                                     |
| Goal             | State what the system shall do and how well, verified and traceable, so planning can rely on it and verification can test against it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| Granularity      | Two levels in one artifact: requirement groups, and atomic requirements that belong to exactly one group. Grouping is structural — the coarser level of the same artifact. An atomic requirement states one behavior, or one quality attribute target.                                                                                                                                                                                                                                                                                                                                                                             |
| Owner / approver | `requirements-engineer` (sole editor and verifier; self-verification is accepted) / requester or user, for a change of meaning                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| Produced by      | Phase 2 Requirements, `requirements-engineer`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Lifecycle        | `draft` → `verified`; a requirement that is removed is `archived`. A failed verification leaves it `draft` and records the result as `gaps` or `blocked`. No version history: a change replaces the current text.                                                                                                                                                                                                                                                                                                                                                                                                                  |
| Required fields  | Requirement group: identifier, title, scope description, user story.<br/>Business requirement (REQ): identifier, group, title, user story, description, acceptance criteria (testable and unambiguous), references to the request and related requirements.<br/>Non-functional requirement (NFR): identifier, group, description with an observable and achievable target, quality attribute or constraint named in the rationale, verification method, references.<br/>All: status (`draft`, `verified`, `archived`). Identifiers are two-level: group `REQ-001` or `NFR-001`; atomic requirement `REQ-001.002` or `NFR-001.002`. |
| Dependencies     | request item it fulfills; glossary terms; domain objects; decisions                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| Dependents       | business rules; technical specification sections; backlog; tasks; milestones; architecture; test cases                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Related          | related requirements                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| Never contains   | Solution design, architecture decisions, technology, business rule statements, UI design, tasks, task-level acceptance criteria, execution evidence, estimates, and code.                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| Verified by      | Phase 2 verification, per requirement; Phase 5 verification against the requirement acceptance criteria, which may be satisfied across several tasks; Phase 6 release quality audit, for NFR coverage.                                                                                                                                                                                                                                                                                                                                                                                                                             |
| Notes            | Corpus-level verification in Phase 2 (no duplicates or contradictions, terminology consistency, listability) applies to the set of requirements, not to a single requirement.<br/>Priority and timing are not requirement fields: whether and when a need is fulfilled is decided through the request lifecycle and planning.<br/>No versioning: the corpus is the current truth for the task at hand; a correction replaces the text.                                                                                                                                                                                             |

### Business Glossary

| Field            | Content                                                                                                                                                                                        |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The canonical meaning of each business term used by the project.                                                                                                                               |
| Goal             | Maintain one canonical meaning per business term, so requirements, rules, domain model, specifications, UI text, tasks, and code use the same language.                                        |
| Granularity      | One entry per term and meaning. A term with more than one meaning gets one entry per meaning, each qualified; meanings are never merged.                                                       |
| Owner / approver | `terminologist` (sole editor and verifier; self-verification is accepted) / requester or user, for a change of meaning                                                                         |
| Produced by      | Phase 2 Requirements, delegated to `terminologist`                                                                                                                                             |
| Lifecycle        | `draft` → `verified`; a deprecated term is `archived`.                                                                                                                                         |
| Required fields  | canonical term, definition, synonyms, acronyms and abbreviations, cross-references                                                                                                             |
| Dependencies     | none: the glossary is an independent source of truth                                                                                                                                           |
| Dependents       | requirements; business rules; domain model; technical specification; UI specification; tasks; source code                                                                                      |
| Related          | other terms, through cross-references                                                                                                                                                          |
| Never contains   | Entity and attribute design (domain model) and code identifiers.                                                                                                                               |
| Verified by      | Phase 2 verification by `terminologist`: one meaning per term, no term carries two unqualified meanings, and every business term used in requirements and rules resolves to exactly one entry. |
| Notes            | No usage index: where a term is used is not recorded here; coverage is checked from the consumers.                                                                                             |

### Domain Model

| Field            | Content                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The conceptual model of the business domain — its contexts, objects, states, attributes, and processes — described independently of implementation.                                                                                                                                                                                                                                                                                                               |
| Goal             | Describe the business domain independently of implementation, so requirements are understood in their real context and solutions use consistent concepts.                                                                                                                                                                                                                                                                                                         |
| Granularity      | One domain model for the system, composed of multiple views: context map, business object model, state diagrams, attribute lists, and business process diagrams. No versioning.                                                                                                                                                                                                                                                                                   |
| Owner / approver | `domain-modeler` (sole editor and verifier; self-verification is accepted) / requester or user, for a change of business meaning                                                                                                                                                                                                                                                                                                                                  |
| Produced by      | Phase 2 Requirements, delegated to `domain-modeler`                                                                                                                                                                                                                                                                                                                                                                                                               |
| Lifecycle        | Per file: `draft` → `verified`; a removed file is `archived`. No versioning.                                                                                                                                                                                                                                                                                                                                                                                      |
| Required fields  | context map, business object model, state diagrams, attribute lists, business process diagrams; an identifier per file, chosen by `domain-modeler`, not following another artifact's identifier pattern                                                                                                                                                                                                                                                           |
| Dependencies     | business glossary                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| Dependents       | requirements; business rules; technical specification                                                                                                                                                                                                                                                                                                                                                                                                             |
| Related          | none: relationships between contexts live in the context map, inside this artifact                                                                                                                                                                                                                                                                                                                                                                                |
| Never contains   | Technical architecture, code structure, UI design, and API or persistence details.                                                                                                                                                                                                                                                                                                                                                                                |
| Verified by      | Phase 2 verification by `domain-modeler`: every context, object, state, attribute, and process is defined once; terminology matches the glossary; conflicts are resolved with the requester.                                                                                                                                                                                                                                                                      |
| Notes            | Structure is free: the model lives in a folder as a set of files, each carrying its own identifier and `draft`, `verified`, or `archived` status.<br/>The identifier is chosen by `domain-modeler`; the only constraint is that it does not follow the identifier pattern of another artifact.<br/>Attributes here are business attributes: name, meaning, and business constraints. Types, serialization, and persistence belong to the technical specification. |

### Business Rules

| Field            | Content                                                                                                                                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | A statement of decision logic — a rule, formula, or constraint — required for the fulfillment of a requirement.                                                                                         |
| Goal             | State the decision logic and constraints of the business domain that implementation must obey. Every rule must help fulfill a requirement.                                                              |
| Granularity      | One rule per decision, formula, or constraint. A rule is stated independently, is never embedded in a requirement, and traces to every requirement it helps fulfill.                                    |
| Owner / approver | `business-analyst` (sole editor and verifier; self-verification is accepted) / requester or user, for an open business decision                                                                         |
| Produced by      | Phase 2 Requirements, delegated by `requirements-engineer`; updated when a served requirement changes                                                                                                   |
| Lifecycle        | `draft` → `verified`; when a served requirement changes, every rule that references it returns to `draft` until re-verified; a rule that is removed is `archived`.                                      |
| Required fields  | identifier, rule statement, applicability, exceptions, at least one worked example, source requirement references                                                                                       |
| Dependencies     | requirement it helps fulfill; glossary terms; domain objects                                                                                                                                            |
| Dependents       | technical specification sections; UI specification; tests                                                                                                                                               |
| Related          | none                                                                                                                                                                                                    |
| Never contains   | Requirements, technical validation logic, UI behavior, and code.                                                                                                                                        |
| Verified by      | Phase 2 verification by `business-analyst`: consistent with the requirements it serves, no overlap with another rule, no conflict with another rule; Phase 5, through the tests that exercise the rule. |
| Notes            | Rule shape is free: a typed rule is the norm, prose is allowed when a rule cannot be typed.<br/>A rule does not change the glossary or the domain model; those are inputs.                              |

### Backlog

| Field            | Content                                                                                                                                                                                                               |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The project-level planning container: the roadmap, with its milestones, tasks, and releases.                                                                                                                          |
| Goal             | Turn verified requirements into an ordered, dependency-safe delivery plan that the orchestrator can execute without re-planning.                                                                                      |
| Granularity      | One per project. It groups the milestones, tasks, and releases of the whole project.                                                                                                                                  |
| Owner / approver | `planner` (owner, accountable for the plan) / user, for priority and scope decisions                                                                                                                                  |
| Produced by      | Phase 3 Planning, `planner`; corrected by re-planning                                                                                                                                                                 |
| Lifecycle        | No status: the backlog is a grouping concept, not an executable item. Status lives on tasks; milestone completion is derived.                                                                                         |
| Required fields  | Roadmap: ordered features with requirement references and rationale.<br/>Milestones, tasks, and releases of the project, excluding archived ones, each with its own required fields.                                  |
| Dependencies     | none: the backlog is a grouping concept, not a planned item                                                                                                                                                           |
| Dependents       | none                                                                                                                                                                                                                  |
| Related          | none                                                                                                                                                                                                                  |
| Never contains   | Requirements, task-level acceptance criteria (`task-refiner`), architecture decisions, source code, and approval decisions.                                                                                           |
| Verified by      | Phase 3 plan validation: required task sequence per milestone, acyclic dependency graph, every dependency scheduled earlier, every requirement mapped to a task, unambiguous ordinals; re-run after each re-planning. |
| Notes            | Coordination artifact: edited by `planner`, `task-refiner`, the assigned actors, and the orchestrator; the planner owns the result.<br/>Archived tasks, milestones, and releases are not listed in the backlog.       |

### Task

| Field            | Content                                                                                                                                                                                                                   |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The atomic unit of planned work inside a milestone, including its refinement and its fulfilment proof.                                                                                                                    |
| Goal             | Turn one piece of a milestone into a unit that can be planned, refined, executed, verified, and closed.                                                                                                                   |
| Granularity      | One atomic piece of work. A task belongs to exactly one milestone and is never shared between milestones.                                                                                                                 |
| Owner / approver | `planner` (creates every task; owns plan fields); the triggering actor defines a task's content, e.g. a reviewer for a correction or fix task; `task-refiner` (refinement fields); assigned actor (executes); `orchestrator` (`status`) / `Done` requires fulfilled acceptance criteria and, when the task's artifact requires it, the user's verification; no other approval                                        |
| Produced by      | Phase 3 Planning, `planner`; the `planner` also creates verification, correction, and fix tasks in Phases 5 and 6 at the triggering reviewer's request; refined in Phase 4 by `task-refiner`; executed in Phase 4                                                                                                                                    |
| Lifecycle        | `To Do` → `In-Progress` → `Done`; `archived` when cleaned up, which hides it from the backlog. `Done` when every acceptance criterion is fulfilled and any required artifact verification is obtained.                                                                       |
| Required fields  | Planning: identifier, title, milestone, ordinal, assigned actor, `Dependencies`, source requirement, `bug` request, or `technical-improvement` request (with the recorded reason when no requirement is produced), status.<br/>Refinement: task scope, behavior, acceptance criteria.<br/>Execution: fulfilment proof.<br/>Milestone verification task: package evidence — version, commit SHA, scripts, component archives, paths, sizes, sha256 — or the recorded waiver. |
| Dependencies     | requirements (REQ/NFR); affected technical specification subsections; test cases; other tasks it depends on                                                                                                               |
| Dependents       | tasks that depend on it; source code; milestone verification task                                                                                                                                                         |
| Related          | none                                                                                                                                                                                                                      |
| Never contains   | Requirements, architecture decisions, specification content, source code, and approval decisions.                                                                                                                         |
| Verified by      | its acceptance criteria, fulfilled and proved; Phase 5 milestone verification, which may reopen it.                                                                                                                       |
| Notes            | Coordination artifact: edited by `planner`, `task-refiner`, the assigned actor, and the orchestrator.<br/>The task is a generic artifact: an implementation task, a milestone verification task, a correction task (milestone or release), or a fix task, among others.<br/>A milestone verification task is a normal task used at the milestone boundary; it is not a separate artifact.   |

### Milestone

| Field            | Content                                                                                                                                                                                                   |
| ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | A delivery increment containing the tasks of one enhancement, one technical improvement, or a batch of `bug` fixes.                                                                                           |
| Goal             | Group the tasks of one increment so they are delivered and verified as a unit.                                                                                                                            |
| Granularity      | One per enhancement, one per technical improvement, or one per batch of `bug` tasks. A milestone contains tasks and belongs to exactly one release.                                                           |
| Owner / approver | `planner` (creates and assigns) / `quality-gatekeeper`, which confirms completion through milestone verification                                                                                          |
| Produced by      | Phase 3 Planning, `planner`                                                                                                                                                                               |
| Lifecycle        | Completion is derived from its tasks and confirmed by milestone verification in Phase 5. `archived` when cleaned up, which hides it from the backlog.                                                     |
| Required fields  | identifier, title, kind (`bug`, `enhancement`, `technical-improvement`), included tasks, release assignment, acceptance criteria (each with an identifier and a testable statement, traceable to REQ/NFR, or to the `bug` request(s) of a bug-batch milestone) |
| Dependencies     | the requirements it delivers                                                                                                                                                                              |
| Dependents       | milestone verification task                                                                                                                                                                               |
| Related          | other milestones, through roadmap order                                                                                                                                                                   |
| Never contains   | Task-level acceptance criteria (`task-refiner`), execution status, and approval decisions.                                                                                                                |
| Verified by      | Phase 5 milestone verification, including the published RC package for the recorded version.                                                                                                                                                                           |
| Notes            | The RC package is published by the orchestrator with `packaging` into the git-ignored `builds/<version>/` using each component's own script; its evidence lives in the milestone verification task, not on the milestone record. |

### Release

| Field            | Content                                                                                                                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Definition       | A version record that owns one or more verified milestones and records the final version.                                                                                                                                                                          |
| Goal             | Group verified milestones into one releasable scope, and record the final version and its completion after user approval.                                                                                                                                          |
| Granularity      | One per release; it owns one or more milestones, and a milestone belongs to exactly one release.                                                                                                                                                                   |
| Owner / approver | `planner` (composition and milestone assignment); `orchestrator` (final version and completion) / user, who approves scope, findings, and the release                                                                                                              |
| Produced by      | Phase 3 Planning, `planner`; completed in Phase 6 by `orchestrator`                                                                                                                                                                                                |
| Lifecycle        | `open` → `completed`; `archived` when cleaned up. The milestone composition stays dynamic while the release is `open`: milestones can be added.                                                                                                                    |
| Required fields  | owned milestones and release scope, RC versions from Phase 5, the final version, package evidence (component archives, paths, sizes, sha256) or the recorded packaging waiver, and completion note                                                                                                                                                               |
| Dependencies     | milestone verification (RC versions)                                                                                                                                                                                                                               |
| Dependents       | release report                                                                                                                                                                                                                                                     |
| Related          | none                                                                                                                                                                                                                                                               |
| Never contains   | Release report content, audit findings, and the approval decision itself.                                                                                                                                                                                          |
| Verified by      | Phase 6 release inspection — release quality, code, and security audits, final build and tests — the published final package, and the user's release approval.                                                                                                                                  |
| Notes            | The final version is chosen after the scope and findings approval and before the final build.<br/>The final package is published locally under `builds/<version>/` and never committed, tagged, pushed, or uploaded.<br/>The release has no acceptance criteria of its own; project-wide criteria apply to it.<br/>A fix milestone is added when an audit fails or a finding is rejected. |

### Architecture

| Definition       | The design principles, properties, and evolution strategy of the system.                                                                                                                                                                                                                                                                                                                                                  |
| Goal             | Fix the fundamental structure, global solution design, and technology stack so that quality requirements are met and the system can evolve coherently.                                                                                                                                                                                                                                                                    |

No versioning.                                                                                                                                                                                                                                                                                                    |
| Owner / approver | `architect` (sole editor and verifier; self-verification is accepted) / user, who verifies the architecture; a positive verification approves it                                                                                                                                                                                                                                                                          |
| Produced by      | Phase 4, architecture impact assessment task kind; the first assessment establishes the baseline                                                                                                                                                                                                                                                                                                                          |
| Lifecycle        | Per file: `draft` → `verified`; `archived` when cleaned up. No versioning.                                                                                                                                                                                                                                                                                                                                                |
| Required fields  | context, building block, runtime, and deployment views; global solution design; technology stack selection (languages, frameworks, platforms, infrastructure); external interfaces and contracts; cross-cutting concepts                                                                                                                                                                                                  |
| Dependencies     | requirements; decisions                                                                                                                                                                                                                                                                                                                                                                                                   |
| Dependents       | technical specification                                                                                                                                                                                                                                                                                                                                                                                                   |
| Related          | none                                                                                                                                                                                                                                                                                                                                                                                                                      |
| Never contains   | Requirement content, detailed design, source code, acceptance criteria, and building-block specifications (Technical specification).                                                                                                                                                                                                                                                                                      |
| Verified by      | Phase 4: the user verifies the architecture; the positive verification approves it before dependent design and implementation.                                                                                                                                                                                                                                                                                             |
| Notes            | The architecture lives in a folder; its files have no defined identifier scheme.<br/>Building blocks are the sections of the Technical specification; an architecture element has no artifact of its own.<br/>The architecture is updated by the architecture impact assessment at every milestone; the first assessment establishes the baseline.<br/>An architecture decision is a `Decision` with type `architecture`. |

### Decision

| Field            | Content                                                                                                                                    |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Definition       | A documented trade-off choice made by the user, when the resolution is not obvious across stakeholders and an in-depth record is required. |
| Goal             | Preserve the reasoning behind a non-obvious trade-off, so later work follows it or supersedes it knowingly.                                |
| Granularity      | One per trade-off. A business decision sits at requirement level; an architecture decision at technical level.                             |
| Owner / approver | `user` (triggers and decides); documented by the owner of the affected artifact (`requirements-engineer` or `architect`) / user            |
| Produced by      | Triggered by the user in any phase; documented by the affected owner                                                                       |
| Lifecycle        | `proposed` → `accepted` → `deprecated`; `proposed` → `rejected`; `accepted` → `superseded`.                                                |
| Required fields  | identifier, title, type (`business`, `architecture`), decision, context, consequences, references (between decisions, for supersession)    |
| Dependencies     | none: triggered by the user                                                                                                                |
| Dependents       | requirements; architecture; technical specification                                                                                        |
| Related          | other decisions, through supersession                                                                                                      |
| Never contains   | Requirement content, detailed design, and source code.                                                                                     |
| Verified by      | Acceptance by the user.                                                                                                                    |
| Notes            | Only the user triggers a decision; anyone may request one.                                                                                 |

### Technical specification

| Field            | Content                                                                                                                                                                                                                                                                                                                    |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The project-wide description of the system's technical properties, organized in sections per part of the system.                                                                                                                                                                                                           |
| Goal             | Turn verified requirements and architecture decisions into an implementation-consumable specification that implementation and verification can rely on.                                                                                                                                                                    |
| Granularity      | One specification for the whole project, organized in sections per building block of the architecture, each divided into subsections. At least one section per building block. A feature does not get its own specification: it updates the sections it affects.                                                           |
| Owner / approver | `tech-writer` (sole editor) / `architect`, who approves conformance with the architecture and decisions                                                                                                                                                                                                                    |
| Produced by      | Phase 4, after the architecture impact assessment; created by `tech-writer`, updated by any milestone that affects it                                                                                                                                                                                                      |
| Lifecycle        | Per file: `draft` → `verified` (conformance approved by `architect`); `archived` when cleaned up. No versioning.                                                                                                                                                                                                           |
| Required fields  | Content: section identifier (`SPEC-001`); subsection identifiers (`SPEC-001.01`); behavior; flows and states; data and API-facing attributes; validation and error behavior; interface contracts.<br/>References (metadata, not body): `REQ`/`NFR`, `BR`, `ADR`, glossary, and domain IDs. |
| Dependencies     | requirements (REQ/NFR); architecture, for its building blocks; decisions; business rules; business glossary; domain model                                                                                                                                                                                                  |
| Dependents       | tasks                                                                                                                                                                                                                                                                                                                      |
| Related          | other sections, when a section builds on another                                                                                                                                                                                                                                                                           |
| Never contains   | Business requirements, acceptance criteria, roadmap order, source code, traceability lists, and Task/Milestone/Release references.                                                                                                                                                                                |
| Verified by      | Phase 4: `architect` confirms conformance with the architecture and decisions before refinement; Phase 5 verifies the behavior changed in the milestone.                                                                                                                                                                   |
| Notes            | Sections follow the building blocks of the architecture; an architecture element has no artifact of its own.<br/>A section is a building block; its subsections hold the specification content, and tasks depend on subsections.<br/>The body documents behavior only; traceability is attached as references. A task references the section, never the reverse. |

### UI Specification

| Field            | Content                                                                                                                                                                                                                                                                                                                                               |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | A corpus of user-interface specifications for the project, ordered in sections and subsections.                                                                                                                                                                                                                                                       |
| Goal             | Describe the user interface precisely enough that design, implementation, and review work from one shared understanding of its layout, navigation, states, and interaction.                                                                                                                                                                           |
| Granularity      | One corpus per project. Each specification is an entry with an identifier, a title, a status, and a body; entries are organized in sections and subsections. The theme grouping is proposed by `ui-designer` from the project goals and requirements and approved by the user.                                                                        |
| Owner / approver | `ui-designer` (sole editor and verifier; self-verification is accepted) / user                                                                                                                                                                                                                                                                        |
| Produced by      | Phase 4, UI design task kind; updated whenever an affected theme changes                                                                                                                                                                                                                                                                              |
| Lifecycle        | Per entry: `draft` → `verified` → `archived`.                                                                                                                                                                                                                                                                                                         |
| Required fields  | identifier, title, status, body                                                                                                                                                                                                                                                                                                                       |
| Dependencies     | requirements; business rules; business glossary                                                                                                                                                                                                                                                                                                       |
| Dependents       | UI mockups                                                                                                                                                                                                                                                                                                                                            |
| Related          | none                                                                                                                                                                                                                                                                                                                                                  |
| Never contains   | Technology and library choices, production styling assets, backend behavior, clickable prototypes, and validation rules or error semantics.                                                                                                                                                                                                           |
| Verified by      | Phase 4: the user verifies the interface at the mockup; a positive verification approves it. Phase 5 verifies the implemented interface against it.                                                                                                                                                                                                                    |
| Notes            | The body holds the description in prose or a typed form: layout regions, navigation, UI states, interaction behavior, presentation of validation and messages, and platform differences.<br/>The specification describes presentation and interaction; validation rules belong to business rules, and error semantics to the technical specification. |

### UI Mockups

| Field            | Content                                                                                                                                                                                                                                                                                                    |

| Lifecycle        | `draft` → `approved` (a positively completed user verification) → `archived`.                                                                                                                                                                                                                              |
| Required fields  | identifier, title, affected task, platforms covered, the mockup, a review landing, navigation between the described interfaces                                                                                                                                                                             |

| Dependents       | none                                                                                                                                                                                                                                                                                                       |
| Related          | none                                                                                                                                                                                                                                                                                                       |
| Never contains   | Production styling assets, technology choices, backend behavior, the UI specification itself, and the mockup's technical definition.                                                                                                                                                                       |

### Test Case

| Field            | Content                                                                                                                                |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The description of an integration test, written as a Gherkin scenario (`GIVEN` / `WHEN` / `THEN`): the behavior to exercise and the outcome it must produce. |
| Goal             | State which integration test verifies a requirement and its business rules, so implementation and verification run the same test.      |
| Granularity      | One per verification scenario, covering one requirement and the business rules attached to it.                                         |
| Owner / approver | `test-manager` (sole editor) / user, who verifies the test case; a positive verification approves it                                   |
| Produced by      | Phase 4, test design task kind, `test-manager`                                                                                         |
| Lifecycle        | `draft` → `approved` (a positively completed user verification) → `verified` when its implemented test passes; `archived` when cleaned up.                                        |
| Required fields  | identifier, Gherkin scenario (`GIVEN`, `WHEN`, `THEN`), covered requirement, covered business rules                                  |
| Dependencies     | requirement; business rules                                                                                                            |
| Dependents       | task                                                                                                                                   |
| Related          | none                                                                                                                                   |
| Never contains   | Test implementation code, requirements, architecture decisions, and verification evidence.                                             |
| Verified by      | Phase 4: the user verifies the test case; a positive verification approves it. Phase 5: the implemented test passes and covers its requirement.                             |
| Notes            | A test case describes an integration test: does the feature still work. Low-level tests live with the code and are not described here.<br/>One test case holds exactly one Gherkin scenario and one `WHEN` block; variants and boundary outcomes get their own test case.<br/>Steps stay at the behavior level, without implementation detail. |

### Source Code

| Field            | Content                                                                                                                                                                                                                       |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | The executable implementation of a building block: source code with its low-level tests, plus the integration tests that implement the test cases.                                                                            |
| Goal             | Deliver the code with its low-level and integration tests, so acceptance criteria and quality requirements are demonstrably met.                                                                                              |
| Granularity      | One per building block of the architecture. Each deployable component (microservice, Android app, server) has its own independent source code; shared libraries are possible, but every component can be deployed on its own. |
| Owner / approver | the assigned `*-dev` agent / none: the work closes when the fulfilment proof is provided on the task                                                                                                                          |
| Produced by      | Phase 4, implementation task kind                                                                                                                                                                                             |
| Lifecycle        | none                                                                                                                                                                                                                          |
| Required fields  | none: the repository defines its own structure. Every deployable building block carries `<component-dir>/scripts/build-package.sh`, committed as source inside the owning `*-dev` agent's component folder (`apps/<app>` in a multi-app repository, or the repository root for a single-app project), per the `build-package-script` contract; components never share one script. |
| Dependencies     | tasks (requirements, specifications, decisions, and test cases are indirect, through the tasks)                                                                                                                               |
| Dependents       | milestone verification task; release final package                                                                                                                                                                             |
| Related          | none                                                                                                                                                                                                                          |
| Never contains   | Requirements, acceptance criteria, plans, design approval, and review verdicts.                                                                                                                                               |
| Verified by      | Phase 5 milestone verification: tests rerun and the code audit; Phase 6 final build, tests, and the package built from each component's script.                                                                                |
| Notes            | The codebase implements both the requirements and the test cases; a test case without an implemented integration test is not covered.<br/>Low-level tests protect the code itself; test cases cover the feature as a whole.<br/>The build script lives in the owning dev agent's component folder so that agent can create and maintain it; it is added by a task when packaging reports it missing, and each packaging run is the check that it still works. |

### Audit

| Field            | Content                                                                                                                                                                                                       |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Definition       | An assessment of a work product against defined criteria, recorded with a type: quality, code, or security.                                                                                                   |
| Goal             | Give an evidence-based, severity-ranked verdict on the assessed scope, so the user can decide acceptance rather than rely on assumption.                                                                      |
| Granularity      | One per check per assessed scope: change-scoped in Phase 5, release-wide in Phase 6.                                                                                                                          |
| Owner / approver | `quality-gatekeeper` (quality), `code-analyzer` (code), `security-officer` (security) / user, who accepts or rejects each finding at the Phase 6 scope-and-findings review; no approval happens in Phase 5                                                                   |
| Produced by      | Phase 5 (types: quality, code); Phase 6 (types: quality, code, security)                                                                                                                                      |
| Lifecycle        | `issued` → `approved` → `archived`; `approved` records the user's acceptance of the findings at the Phase 6 scope-and-findings review, so a Phase 5 milestone audit remains `issued` until then. A finding the user does not accept becomes correction or fix work and a new audit is issued; the old one is `archived`. Only one audit of a type can be `issued` or `approved` within a single assessed scope (one milestone in Phase 5, one release in Phase 6) at a time; when a check is rerun after a correction, the new audit replaces the previous one, which is `archived`. |
| Required fields  | identifier, title, type (`quality`, `code`, `security`), scope, severity-ranked findings with evidence, fix proposal, approval status, and overall verdict/recommendation                                                                     |
| Dependencies     | source code; requirements; technical specification, for the audited scope                                                                                                                                     |
| Dependents       | follow-up tasks created to fix findings                                                                                                                                                                       |
| Related          | other audits of the same scope                                                                                                                                                                                |
| Never contains   | Remediation implementation and functional testing.                                                                                                                                                            |
| Verified by      | not applicable: the audit is the verdict record.                                                                                                                                                              |
| Notes            | Always read-only.<br/>Severity scale: low, medium, high, blocker.<br/>An audit is scoped to one milestone (Phase 5) or one release (Phase 6); within that scope only one audit of a type may be `issued` or `approved` at a time. On a rerun after a correction, the new audit is `issued` and the previous one is `archived`.<br/>Phase 5 code audits are change-scoped to the files touched by the milestone; Phase 6 code audits cover the whole codebase.<br/>In Phase 5, findings are corrected or deferred (owner and follow-up task); acceptance is the user's, at the Phase 6 review. |

## Audit types

- quality audit, checks:
  - acceptance criteria
  - scope creep
  - NFR coverage
- code audit, checks:
  - complexity
  - duplication
  - naming
  - structure
  - test coverage
  - style-guide compliance
- security audit, checks:
  - secrets
  - dependency supply chain
  - authentication and authorization
  - input handling
  - data protection
  - platform-specific risks
  - cross-feature risks

## Acceptance criteria

"The criteria that a work product must satisfy to be accepted by the stakeholders"; in agile development, the criteria that the implementation of a backlog item must satisfy.
